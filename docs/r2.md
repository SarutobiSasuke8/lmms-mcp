# Publishing approved generations to Cloudflare R2

`publish_to_r2` promotes one catalogued generation to a private Cloudflare R2 bucket for games to read. `list_r2_assets` lists what is already there. Both sit on the [generation catalogue](catalogue.md), so a generation must be catalogued first.

Nothing here creates a bucket, a token, a domain or a worker. Those steps are yours. They are described below as plain text.

## What gets written

For a generation published as game `forest`, kind `cue`, slug `theme`, version 1:

| Object | Changes? | Purpose |
| --- | --- | --- |
| `games/forest/cue/theme/v1.ogg` | Never | The audio. One object per audio extension (wav, ogg, mp3, flac). |
| `games/forest/cue/theme/v1.manifest.json` | Never | Hashes, sizes, source facts, licence and credits for this version. |
| `games/forest/cue/theme/manifest.json` | Pointer | Lists every version of the slug and names the latest. |
| `games/forest/index.json` | Pointer | Every asset in the game with its latest version, keys, hashes and credits. Games can load this one file. |

Versioned objects are immutable. Each is uploaded with `If-None-Match: *`, so R2 rejects the write if the key exists. The next publish of the same slug becomes `v2`. The two pointer documents are the only objects that change. They are replaced only with `If-Match` on the version that was read, so two publishers cannot silently overwrite each other.

Keys in the manifests are relative to the bucket root. A game prepends its own base URL.

The manifests never contain local file paths or the recipe arguments. They do contain the credits for every sample library the generation used. Show those credits in the game.

## Using the tools

1. Dry run. Call `publish_to_r2` with `id`, `game` and `kind`. Optionally add `slug` (it defaults to the audio file name) and `files` (needed only when a generation has several audio files with the same extension, such as stems). The reply lists every key, its size and its SHA-256, and says which pointer documents would be created or updated. Nothing is uploaded.
2. Check the output with Alexei. Approval to promote is the `confirm` step.
3. Call it again with `confirm: true`. It uploads the audio, then the version manifest, then the two pointers, and then saves the location in the catalogue (`locations.r2`, for example `r2://my-bucket/games/forest/cue/theme/v1.ogg`).

It refuses to publish when the licence of any library is unknown, when a licence that requires attribution (CC BY, MIT) has no credit recorded, when the catalogue does not mark the generation publishable, when a file no longer matches its catalogued hash, or when identical content is already published for the slug.

If R2 is not configured, the dry run still works but assumes `v1`, and says so. Configure R2 to get the real next version.

## Configuration

Only these four environment variables are read. They are never logged or returned.

| Variable | Value |
| --- | --- |
| `R2_ACCOUNT_ID` | Your 32 character Cloudflare account ID |
| `R2_ACCESS_KEY_ID` | Access key ID of the R2 API token |
| `R2_SECRET_ACCESS_KEY` | Secret access key of the R2 API token |
| `R2_BUCKET` | Bucket name |

Set them in the environment of the process that runs the MCP server (for example the `env` block of your MCP client configuration, or your user environment variables). Do not commit them and do not paste them into chat.

## Setup steps for Alexei

Menu names in the Cloudflare dashboard change from time to time, so treat these as a guide.

1. Sign in to the Cloudflare dashboard and open R2 object storage in the sidebar. If R2 has never been used on the account, accept the plan terms there. Cloudflare may ask for a payment method before R2 is enabled.
2. Create a bucket. Pick a name such as `lmms-game-audio`, keep the default location unless you have a reason to change it, and leave public access off. The bucket stays private. Do not enable the public development URL for it.
3. Note your account ID. It is shown on the R2 overview page and in the dashboard sidebar for the account.
4. Create an API token for R2. In R2 open the API area and choose to create an API token. Give it the Object Read and Write permission, scope it to the one bucket you created (not all buckets), and set an expiry you are comfortable with. Do not give it Admin permissions.
5. Copy the Access Key ID and the Secret Access Key when they are shown. The secret is shown once. Store both in your password manager.
6. Set the four environment variables above on the machine that runs lmms-mcp.
7. Restart the MCP server, run a dry run on a catalogued generation, and read the output before confirming.

## Letting games read the files

The bucket is private, so a game cannot read it directly. Reading in a browser or game needs one of these, which is a later decision for you:

- A custom domain connected to the bucket. Add a CORS rule for your game origins if the game loads files from a web page.
- A worker or other service that checks access and streams objects.

Until then the game build can copy the files it needs out of R2 at build time using the same token.

## Not checked against a live bucket

The code is tested against an in-memory S3 stand-in and against the published AWS Signature Version 4 example. It has not been run against real R2. In particular, create-only uploads depend on R2 honouring `If-None-Match: *` and `If-Match` on PutObject. This was not checked against Cloudflare documentation from this build, so confirm it with a first dry run and a first small publish before relying on it.
